# Implementation Plan — Provider Activation Flow (FIND-U)

Derived from the APPROVED design `design.md` (Tier-3 / HEAVY). This plan sequences the design faithfully; it does not re-decide the architecture. Where the task prompt and the design disagreed on a path, the verified repo location wins and is noted inline.

## Ground truth established during exploration (read before implementing)

- **Backend worktree root:** `findu/.worktrees/provider-activation` on branch `feature/provider-activation` (clean). Use `git -C <that path>` for all backend git.
- **Security micro path is `SECURITY/findu-spring-security`**, NOT `CORE/findu-spring-security` (the task prompt said CORE; the repo and design say SECURITY — verified against README §Estructura and the filesystem). All security paths below are under `SECURITY/findu-spring-security`.
- **Build commands (verified `gradlew.bat` present in each):** from each micro dir run `.\gradlew.bat build` (Windows). Java 21 (Temurin), Spring Boot 3.4.2.
  - security: `SECURITY/findu-spring-security`
  - core: `CORE/findu-core`
  - help-v2: `CORE/findu-help-v2` (has `src/test` with JUnit/Mockito tests)
  - notification-processor: `CORE/findu-notification-processor` (has `src/test`)
- **Mobile app:** `findu-movil/apps/findu_proveedores` is its OWN git repo on branch `master` (findu-movil root is NOT a git repo). Shared packages at `findu-movil/packages/*` are OUTSIDE that repo and are UNVERSIONED — changes there are intentional and must be documented in the final notes. Build/verify with `flutter analyze` and `flutter test` (tests only; never run on device). Env flag mechanism is Dart `--dart-define` / `String.fromEnvironment` (see `lib/core/config/environment.dart`).
- **Mobile navigation convention (verified):** `main.dart` uses `MaterialApp` with `home:` and in-app widget navigation — there is NO named-route table and NO GoRouter. Realtime uses `network_ws` via a `Stream<Map<String,dynamic>>` broadcast (pattern in `features/market/infrastructure/adapters/market_api_adapter.dart`). Therefore the alert `cta_action` deep link must be bound to an in-app navigation handler (not a URL route); the seeded `cta_action` string is a stable identifier the app maps to the biometric screen. The realtime handler branches on `payload["templateCode"]`, not `EventType` (design §6.2/§8.2).
- **Notification trigger (verified):** security uses `NotificationPort.send(type, recipient, templateCode, language, params)` → `NotificationLambdaAdapter` POSTs `{type,recipient,templateCode,language,params}` to `{findu.notification.lambda-url}/dispatchNotification`. Config keys are `findu.notification.lambda-url` and `findu.notification.enabled`. Reuse this verbatim; security never binds to RabbitMQ.
- **QA schema safety (verified):** `application-qa.yml` sets `spring.sql.init.mode=${SPRING_SQL_INIT_MODE:never}`. `schema.sql` begins with `DROP TABLE ...` and is only run manually. Activation DDL must be additive/idempotent and delivered as a standalone migration; do not change the `never` default and do not add DROP for existing tables.
- **Role/operation model (verified in `data.sql`):** existing operation ids run 1–17 (identity, ids omitted in INSERTs and tracked by comment). Roles: 1 CLIENTE, 2 ASSISTANT_ADMIN, 3 ADMINISTRATOR, 4 OUR_PROVEEDOR. `add_soporte.sql` (at the micro root, NOT under `scripts/`) seeds role 5 `ROLE_OUR_SOPORTE` + the `soporte` user (also role 3) and grants role 5 ops 1–12. There is no `scripts/migrations/` dir yet — create it.
- **help-v2 (verified):** Spring MVC + MongoDB, no RabbitMQ. `CreateTicketService` builds a `TicketRequester` from `domain.valueobject.TicketRequester` (there are two VO packages; the service uses `domain.valueobject`). Persistence: `HelpTicketDocument` + `SpringDataHelpTicketRepository extends MongoRepository` + `HelpTicketMongoMapper` + `MongoHelpTicketRepository` adapter implementing `HelpTicketRepository` port. Existing tests: `CreateTicketServiceTest`, `MongoHelpTicketRepositoryTest`.
- **notification-processor (verified):** DynamoDB versioned template engine. Seed is `src/main/resources/db/dynamodb/seed-templates.sh` (bash + aws-cli + jq against LocalStack); each `seed_template` writes `v#1` + `v#ACTIVE`. Attribute names must match `NotificationTemplateItem` constants exactly (as the mapper reads/writes them). For ALERTA, author title/CTA/condition under the `alert_meta` map (keys `categoria`, `pantalla_destino`, `titulo`, `cta_label`, `cta_action`, `cerrable`, `prioridad`, `condicion_aparicion`, `tiempo_desaparicion`), NOT top-level `title`. The seed's `create-table` already declares `GSI_pantalla`, but the Java `DynamoDbTemplateAdapter` wires only `GSI_tipo`; the alert read endpoint must use by-code `findActive(code, ALERTA, lang)` GetItem, no new GSI. Admin create path exists at `POST /api/v1/admin/templates`.
- **core change target (verified):** `GestionPerfilProveedorUseCaseImpl.actualizarPerfil(Long, ActualizarPerfilProveedorRequest)` body currently does unconditional `if (request.urlImagenPerfil() != null) perfil.setUrlImagenPerfil(request.urlImagenPerfil());`. That is the exact write-once edit site.

## Restrictions (enforced throughout)

- Do NOT deploy to Railway or write to real AWS — code + seed script only.
- Keep Mono/Flux reactive style + hexagonal + Lombok in the Spring micros (findu-core is the canonical pattern reference).
- Event/ticket consumers and the support-dispatch guard must be idempotent.
- Do not touch findu-core except the one scoped write-once change on the profile.

## Assumptions carried from the design (flagged)

- `rol_soporte` == `ROLE_OUR_SOPORTE` (id 5). Support is signalled by the help-v2 ticket only (no support presence channel; dispatcher unchanged).
- Name + birth date for biometric comparison come from findu-core's `perfil-proveedor` (security has no such columns).
- Alert visibility is client-side (hybrid); alert content is admin-editable via the template engine.
- Schema change is a manual additive migration against Railway qa; `spring.sql.init.mode=never` is preserved.
- The frontal photo is a URL (uploaded elsewhere); security/core store it write-once.
- The mobile `cta_action` is bound to in-app navigation (no URL router in the app); the stored string is a stable identifier, not a live URL route.
