# Implementation Plan — Verificación de Identidad del Proveedor (OTP celular + email mágico)

Grounded in the real codebase at `SECURITY/findu-spring-security` (Spring Boot 3.4.2, WebFlux reactivo, R2DBC, hexagonal, Java 21, Lombok, MapStruct) and `FRONTEND/proveedor` (Vite + JS vanilla). Build/test: `./gradlew build` and `./gradlew test` from `SECURITY/findu-spring-security` (gradle wrapper present). NOTE: `check` enforces 80% line coverage (`jacocoTestCoverageVerification`); use-case impls are NOT excluded, so each new `application/usecase/impl` class needs unit tests. Adapters under `infrastructure/adapter/persistence|cache` ARE excluded from coverage.

## Design decisions recorded (made during exploration)

- D1. **Fase F — least invasive = extend `/profile`.** The proveedor frontend already drives all post-login routing from `GET /security-auth/api/v1/profile` (`fetchProfile()`), and `AuthToken` is reused by login/register/refresh/logout. So add `phoneVerified`, `emailVerified`, `accountStatus` to `UserProfileResponse` (and the mapping in `JwtManagerImpl.toUserProfileResponse`) instead of changing `AuthToken`. The frontend derives `requiresPhoneVerification` as `!phoneVerified`. Rationale: zero change to the token contract; the data the UI needs already flows through `/profile`.
- D2. **Redis adapter must be conditional + dev fallback.** `RedisReactiveConfig` and the `finduReactiveRedisTemplate` bean exist only when `findu.redis.enabled=true` (dev excludes Redis autoconfig entirely). The Redis `PhoneOtpStorePort` impl is annotated `@ConditionalOnProperty(name="findu.redis.enabled", havingValue="true")`; a second in-memory fallback impl (`@ConditionalOnProperty(... havingValue="false", matchIfMissing=true)`) keeps dev booting and tests green. QA/stage (Railway) has `findu.redis.enabled=true`, so OTP uses real Redis there.
- D3. **Authorization is DB-driven, not just `SecurityConfig`.** `FinduReactiveAuthorizationManager` resolves each request against the `operation` table (module `path_base` + `operation.path` + method) and allows anonymous access only when `permite_all=true`. Therefore new public/authorized endpoints MUST be seeded as rows in `data.sql` (module `security-auth`), mirroring existing AUTH operations. `SecurityConfig` needs no change (swagger stays permitAll).
- D3b. **Authorization decision for the 4 verification endpoints (confirmed with user):** all four are `permite_all=TRUE` (public) AND also granted to `ROLE_OUR_PROVEEDOR` (plus parity roles). Rationale: `GET /email/verify` is opened from the email with no session token, so it must be public; `phone/send-otp`, `phone/verify-otp` and `email/send-verification` must work for a half-registered provider (`phone_verified=false`, `account_status=PENDING_PHONE_VERIFICATION`) without authorization blocking the flow against itself — they are protected by the OTP secret / magic token, exactly like the existing public `forgot-password`/`reset-password`. Granting them to the role too keeps authenticated calls working and leaves room to tighten later. Documented in `docs/verificacion-identidad-proveedor.md`.
- D4. **OTP pattern reused from `RequestPasswordRecoveryUseCaseImpl`**: `String.format("%06d", new SecureRandom().nextInt(999999))`, hashed with `PasswordEncoder`, sent via `NotificationPort.send(...)`. For phone OTP the hash+TTL live in Redis (not BD).
- D5. **`account_status` is a new, independent column.** Existing `estado` (INCOMPLETO/COMPLETO, used by core) is untouched. New state machine: `PENDING_PHONE_VERIFICATION → PENDING_EMAIL_VERIFICATION → DOCUMENTS_PENDING → ACTIVE`.
- D6. **Active frontend files are `FRONTEND/proveedor/main.js` and `/style.css`** (index.html loads `/main.js`, `/style.css` — Vite project root, not `src/`). The `src/` copies are stale and must NOT be edited.
