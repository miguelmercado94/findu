# Canonical provider id (PROVEEDOR_<proveedorId>) across dispatcher, core and app

This change makes `PROVEEDOR_<proveedorId>` the single canonical key for WebSocket handshake, session registry, presence, `canalId` and routing, with a `RecipientResolver` as a transition-window safety net that learns `authUserId -> proveedorId` aliases from the event payload. Core stops double-sending (one `notificationPort.send` per provider) and feeds the alias via additive `canonicalRecipient`/`aliasRecipient` params. The Flutter app opens exactly one canonical socket per screen (always `proveedorId`, never `authUserId`) and the ticket chat reconnects via a `SessionManager` listener. The three previously-open design-review findings (#10 invariant, #8 help-v2 doc, #9 alias-method ownership) are the gating items for this pass.

Watch for: the `canalId == toCanonical(targetUserId)` invariant (#10) is enforced in code for the provider case on all three paths, but the HTTP-presence path has no integration test proving it — the controller test mocks the dispatcher (confirmed). The HTTP presence path also still prefixes bare non-prefixed recipients as `CLIENTE_<x>` while delivery routes on the unprefixed key, a latent asymmetry outside the provider scope (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The canonicalization is anchored at each entry edge. The handshake normalizes `userId` once and uses that single key for `registerSession`, `registerPresence` and the `doFinally` teardown, so there is no double indexing and no orphan sessions (confirmed). The RabbitMQ path derives `canalId` from `toCanonical(targetUserId)` and delivery runs on the same canonical value, so channel state and delivery agree; this path has an explicit test asserting `canalId == PROVEEDOR_42` and that an INACTIVE channel forces FCM (confirmed). `ChannelController` wraps `"PROVEEDOR_" + proveedorId` in `toCanonical`, keeping availability state on the same key.

Alias learning happens exactly once per entry point and never inside `dispatch(String, ...)`: the Rabbit path calls a private `learnAliasFromPayload` in `EventDispatcherService`, and the HTTP presence path calls an inline `aprenderAliasDesdePayload` in the controller. Both read `canonicalRecipient`/`aliasRecipient` defensively and delegate to the idempotent `RecipientResolver.learnAlias`. This resolves the #9 ambiguity (a private-of-another-class that could not be invoked) through a different route than the review suggested — the method was not promoted to a public `RecipientResolver` member — but the design-level defect is gone and both call sites are valid (confirmed).

Core now emits the canonical recipient once and only adds the alias params when `authUserId != proveedorId`, keeping client recipients and business payloads untouched (confirmed via FEAT-002 evidence and the observer test).

The app dropped the secondary socket in both screens, made `_initWebSocket` idempotent, and added the `SessionManager` reconnection hook to the ticket chat so the socket never stays pending once `proveedorId` arrives (confirmed in real code: no `_wsSecondary` references remain, `_onSessionChanged` + `addListener`/`removeListener` present).

The gap is test coverage for #10 on the HTTP presence path, plus a residual non-provider asymmetry in how `despacharEventoPresencia` computes `canalId`.

### #10 invariant — enforced for providers, untested on the HTTP presence path

The invariant `canalId == toCanonical(targetUserId)` holds in code on the three provider paths. In `EventDispatcherService.dispatch(EventEnvelope<?>)` the `canalId` is `toCanonical(targetUserId)` with a fallback to `eventId` only when the canonical is blank, and `procesarEntrega` re-derives the same `toCanonical(envelope.targetUserId())`, so channel history, channel state and delivery all land on one key. `ChannelController.actualizarDisponibilidadProveedor` wraps `"PROVEEDOR_" + proveedorId` in `toCanonical`, so ACTIVO/INACTIVO is evaluated on the same channel that receives events.

The Rabbit path is the only one with a test that actually proves the invariant: `caminoRabbit_derivaCanalIdDelCanonico_yCanalInactivoFuerzaFcm` captures the `agregarEvento` key and asserts it equals `PROVEEDOR_42` (derived from the alias in the payload, not the `eventId`), and that an INACTIVE channel forces FCM even with a local session. The `appVieja_aliasAprendido...` test also confirms that an aliased `targetUserId` routes delivery to the canonical socket.

The HTTP presence path is where the coverage is missing. `NotificationDispatchControllerTest` mocks `EventDispatcherService`, so `dispatch(canalId, envelope, tipoEvento)` is never executed and the test cannot observe whether `canalId` equals `toCanonical(envelope.targetUserId())` for an aliased provider. The context's verification instruction is explicit that the invariant "debe probarse con un test de integración del dispatcher ... en los caminos HTTP de presencia". Enforcement in code without the required integration test leaves #10 not verifiably closed on this path.

```java
// despacharEventoPresencia
String canonicalRecipient = recipientResolver.toCanonical(recipient);
String canalId;
if (canonicalRecipient.startsWith("PROVEEDOR_") || canonicalRecipient.startsWith("CLIENTE_")
        || canonicalRecipient.startsWith("AGENTE_") || canonicalRecipient.startsWith("SOPORTE_")) {
    canalId = canonicalRecipient;                 // provider path: canalId == targetUserId
} else {
    canalId = "CLIENTE_" + canonicalRecipient;    // bare recipient: canalId != targetUserId
}
EventEnvelope<...> envelope = EventEnvelope.of(eventType, canonicalRecipient, payload);
```

For a provider recipient (prefixed, or numeric/aliased that `toCanonical` resolves to `PROVEEDOR_...`) the first branch holds and `canalId == canonicalRecipient == envelope.targetUserId`. For a bare, non-prefixed recipient the `else` branch opens channel state on `CLIENTE_<x>` while `procesarEntrega` normalizes `envelope.targetUserId()` to the unprefixed `<x>` — the same class of channel/delivery split that #2/#10 set out to eliminate, now scoped to non-provider recipients. This does not affect the provider scenarios #10 targets, but it means the invariant is not uniform. Aligning the envelope `targetUserId` with `canalId` (or scoping the invariant explicitly in a comment) would close it cleanly.

### #9 alias-method ownership — resolved via a different route than suggested

The original ambiguity was that the design described `learnAliasFromPayload` as a `private` method of `EventDispatcherService` yet showed it invoked as `recipientResolver.learnAliasFromPayload(...)` from the controller — a private of another class is not invocable. The implementation removed that ambiguity: `EventDispatcherService` owns a private `learnAliasFromPayload(envelope)` called from `dispatch(EventEnvelope<?>)`, and the controller has its own inline `aprenderAliasDesdePayload(payload)`. Both read `canonicalRecipient`/`aliasRecipient` with `instanceof String` guards and delegate to the idempotent `RecipientResolver.learnAlias`. Neither learns inside `dispatch(String, ...)`. The reviewer's suggested fix was to promote the method to a public `RecipientResolver` member shared by both call sites; that was not done, so the two call sites duplicate a small defensive block. The defect (ambiguous, non-invocable ownership) is resolved; the duplication is a minor style trade-off, not a correctness issue.

### #8 help-v2 doc — corrected

`design.md` now derives canonicity from `requesterUserId`: `create_ticket_screen -> createTicket(userId: proveedorId) -> TicketRequester.userId = proveedorId -> requesterUserId = proveedorId`, so `PROVEEDOR_<requesterUserId>` is canonical, and the `getSenderId()` fallback is flagged as an invariant to harden. The earlier evidence that conflated `senderId` with `requesterUserId` is gone.

### Handshake single-key lifecycle

`EventWebSocketHandler.handle` computes `canonicalUserId = toCanonical(userId)` once and uses it for `registerSession`, `registerPresence`, and in the `doFinally` for `unregisterSession` and `removePresence`. One key in, same key out — no double indexing, no orphaned presence on disconnect.

### App: single canonical socket and ticket-chat reconnection

Both screens build the URL from `proveedorId` and no longer declare or open `_wsSecondaryClient`. `ticket_detail_chat_screen` registers `SessionManager().addListener(_onSessionChanged)` in `initState`, reopens in `_onSessionChanged` when `_wsClient == null` and `proveedorId > 0`, and removes the listener in `dispose`; `_initWebSocket` returns early if a client already exists or `proveedorId` is invalid, so it is idempotent and never leaves the socket pending once the id arrives.

Not tested: FEAT-003 records that the widget tests for these screens could not be used (they trigger real HTTP adapters and leave periodic timers pending — a pre-existing teardown failure), so CA3 ("one WebSocketClient per screen") is covered only by unit tests asserting the URL shape, not by a widget test that counts instantiated clients. The 5 Flutter test failures are recorded as pre-existing and verified via `git stash`.
